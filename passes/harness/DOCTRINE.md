# Harness Pass Doctrine

This doctrine specializes `/srv/harness-ops.md` for a pass whose subject is a completed ordinary-engineering trajectory and whose beneficiary is a future ordinary agent. It does not repeat or replace the shared doctrine.

## 1. Improve the future execution path

Start from concrete trial, error, repeated recovery, stale routing, waiting, correction, risk, or carrying cost in the completed trajectory. Find the earliest authoritative owner whose change would prevent or shorten that cost for a comparable future job.

The intervention is not the explanation of the learning. It is the place a future agent will encounter the learning before repeating the cost.

Prefer placement in this order: executable behavior; deterministic validation or tests; essential entry routing; an already-discoverable recurring procedure; unfinished qualification or dated proof. Documentation-only work is an execution improvement only when the document is already on the governed action's required route or the intervention establishes that short route.

## 2. Preserve ordinary focus

Ordinary agents should not need to read pass methodology. Move accepted knowledge into the ordinary owner's code, tests, defaults, errors, maps, or procedures. Keep pass-specific reasoning in `docs/passes/` and out of ordinary mandatory context.

Do not continue or replay the product job merely to create evidence. Do not use a harness pass to repair a newly discovered product defect unless the current request explicitly authorizes that work.

## 3. Resist overfitting and entropy

One frustrating occurrence does not automatically justify a permanent instruction. Prefer a clear recurring mechanism, a consequential correctness or safety failure, corroborating trajectories, or an owner gap that is independently evident.

Prefer changing, merging, or removing an existing surface over adding another. Do not encode a growing list of incident-shaped prohibitions when a default, narrow adapter, validation guard, clearer failure, or shorter route can make the correct path natural.

Account for active context and carrying cost. A new instruction should eliminate more future recovery than it adds in reading, choice, synchronization, and maintenance. Historical evidence belongs outside active maps; Git already preserves change history.

## 4. Prove encounter, not merely delivery

Delivery proves that an artifact exists. Qualification asks whether a later comparable agent encountered it, used it, reduced the targeted cost, and preserved outcome quality, authority, proof, portability, and recovery.

Every intervention must name its expected future encounter point and a natural comparable exposure. Record `retain`, `revise`, or `remove` only from owner-specific exposed evidence. Unrelated work, unexposed passes, and implementation self-tests do not qualify behavioral efficiency.

## 5. Compact continuously

Keep the mode `AGENTS.md` a short routing map. Add a deeper pattern or proof artifact only when a named trigger makes selective loading useful. Every active artifact needs an owner, route, evidence basis, and retirement condition.

When a lesson becomes executable, delete or compact the explanatory workaround. When guidance becomes stale, duplicated, unreachable, or superseded, remove it from active context while preserving only the evidence still worth keeping.
